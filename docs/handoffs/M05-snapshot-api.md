## 2. Executive summary

Phase 5 is complete. A caller posts one route candidate and its canonical module 04 records. The service drops evidence that was learned after the recommendation time, builds the module 06 features, scores quality over five weighted dimensions, buffers the route corridor in PostGIS and stores an immutable `IntegratedTravelContext`. A replay returns the first snapshot. The same `request_id` with other content returns 409, and a refresh links to the snapshot it replaces through `supersedes_snapshot_id`. An unavailable source stays `null` from the request to the stored feature, so a missing provider never looks like a safe route.

## 4. Behavior and flows

1. `POST /internal/v1/snapshots` validates the body strictly, then hashes it canonically to get `input_content_hash`.
2. If a stored snapshot has the same `request_id` and input hash, it is returned with 200. If the `request_id` exists with a different hash, the answer is 409 `IDEMPOTENCY_CONFLICT`.
3. `build_route_snapshot` runs the pipeline: cutoff → `sample_route` → `build_features` → dedup severity conflicts → `measure_dimensions` → `summarize_quality` → PostGIS `geometry_health` → `corridor_buffer_geojson` → `assemble_snapshot`.
4. `SnapshotRepository.save` inserts the snapshot and checks that the `supersedes` target exists (404 if not). The table trigger from Phase 1 blocks any later UPDATE or DELETE.
5. `POST /{id}/validate` re-validates the stored JSON against the model and recomputes the content hash. It then reads the gate; with `strict`, only PASS is valid.

## 5. Architecture and design

| Path | Role |
| --- | --- |
| `app/pipeline/quality.py` | Dimensions, weighted score, gate; staleness from producer status |
| `app/domain/snapshot.py` | Strict `IntegratedTravelContext`, `TravelWindow` |
| `app/pipeline/snapshot.py` | Assembly, content hash without identity and time, gate-to-status mapping |
| `app/pipeline/spatial.py` | `corridor_buffer_geojson` per dateline part |
| `app/pipeline/build.py` | End-to-end pipeline for one route |
| `app/api/snapshots.py` | Three endpoints and request models |
| `app/main.py`, `app/api/envelope.py` | Contract error envelope for request validation (paths only, values never echoed) |
| `packages/contracts/openapi/internal-data-integration.yaml` | §5.3 contract (#66) |
| `packages/contracts/examples/real-sanitized/integrated-travel-context.bangkok-route.json` | Snapshot generated by the running service |

Decisions:
- **One route per snapshot** (owner decision): the flat `features` map then belongs to exactly one route, which matches module 06's `prediction_unit`.
- The content hash leaves out `snapshot_id`, `created_at` and `content_hash`. Otherwise every replay would look like new content.
- The corridor is buffered per dateline part, because one geography buffer over a line crossing 180° picks a projection spanning the globe.
- The gate travels in `quality_summary.notes` until the contract has a field for it (#63).

## 7. Database and storage

No new migration. The service uses `integration.snapshots` from `0001`/`0002`: the unique `(request_id, input_content_hash, schema_version)` key, the `supersedes_id` FK and the immutability trigger. `route_corridor` now stores the buffered polygon.

**Local environment warning:** a database that ran an earlier, pre-rebase version of these migrations can hold an old `integration.snapshots` shape (for example `gate_outcome`, `quality_json`) while `alembic_version` already reads `0005`. Alembic then skips the migration, and `POST /internal/v1/snapshots` returns 503 (`column "evidence_json" does not exist`). This happened on the author's dev database. It was not reset; the smoke test ran against a fresh database instead. To fix it locally, drop the `integration` schema's M05 tables or recreate the local database, then run `alembic upgrade head`.
